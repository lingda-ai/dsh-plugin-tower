# 塔台（Tower）产品论证 · v0.1

> 立场：AI 产品经理 + 该产品的第一个用户。
> 方法：第一性原理拆「价值从哪来」→ 用本机实测的扩展面与装机现状证伪候选方向 → 给一个能收费的窄口。
> 所有数字要么可复算，要么标注为假设。**假设不等于事实，本文把两者分开写。**

---

## 0. 一句话

**Agent 时代的塔台：当你有多个 AI 在飞，它是唯一告诉你「谁在飞、谁卡住、谁等你」并让你就地放行的那块屏。**

不是又一个文件预览器，不是又一个 token 仪表盘，也不是又一个侧边聊天 ——
是**人机交接面的调度层**：把「轮询多个会话」变成「值守一张台」。

---

## 1. 第一性原理：这个产品的价值从哪来

把「用 agent 干活」拆到底，只有四个不可再分的环节：

```
意图 ──▶ 上下文 ──▶ 动作 ──▶ 验收
 │          │          │        │
写清楚      装得下     敢让它做   确认对不对
```

每一环都有成本：意图写不写清（认知）、上下文够不够（token）、动作敢不敢放（信任）、验收要多少眼（注意力）。

**关键判断：这四环里，已经被商品化的是「上下文」和「验收」。**

- 上下文：上下文窗口、压缩、pruner、spill、模型选型 —— 宿主和模型厂在卷。
- 验收：diff、review、deliverables、turn-review 类插件 —— 生态里已经挤满。

**「动作」这一环长期被当成设置项（权限、审批），却没有人把它当成一个界面问题。**
而 agent 越自主，这一环越贵：目标会自己续轮、作业会自己跑、定时任务会自己开会话。
每一次自主执行都在向人**借信任**，而借据没有账本。

于是有一个反常但扎实的结论：

> **agent 越强，人的瓶颈越从「怎么做」移到「要不要继续」。**
> 界面该优化的不是「给更多信息」，而是「更少次决策」。

塔台只做一件事：把「要不要继续」压缩成**一次点击**，并把「有没有事」压缩成**一个数字**。

### 推论：为什么右侧栏是它的正确位置

右侧栏是**你干活时一直亮着的那块屏**。左侧是导航（去哪），中间是对话（做什么），
右侧天然是**参考与操纵**（看着什么、拨什么）。把「运行中的东西」放右侧栏，
才能在**不离开当前会话**的前提下干预另一个 agent —— 这是左侧列表做不到的，
因为点左侧列表就等于切换了当前上下文。

## 2. 我怎么找到这个问题的（证据，不是感觉）

### 2.1 先量扩展面：宿主到底开放了什么

- 本 profile 的 loader 条目 **206** 条；宿主 Service **约 100 个**。
- 与本问题直接相关、且已经暴露给前端的：`goals`（`get/pause/resume/complete/edit/clear` 均为 `@Remote`）、
  `jobs`（`list/kill`）、`schedule`（`catalog/run/edit/list`）、`agents.turnBoundaryOf()`。
  **也就是说：能力已经开好了，缺的是界面。**
- 右侧栏 tab 容器 `sidebar.right.pane.tab` 在安装本插件前已有 **16 个占用者**
  （内置 guide/document/terminal/files/browser/subagent/plan/deliverables/schedule + better-sidebar 的
  editor/git/subagent/sidechat/diff/files + 账本）。

### 2.2 再量真空区：谁没被做

在**整份实时 slot 清单**里搜索 `goal`，只有一处命中，而且是 `create_goal` / `update_goal`
这两个**工具名**。也就是说：

> agent 可以创建、暂停、完成一个目标；**人在界面上没有任何地方能看到这个目标，更没有任何地方能暂停它。**

这不是「做得不好」，是「没有」。这是本次选型的决定性证据。

同时 `jobs`（后台作业）只有会话内的输出窗口，没有「全机作业」视图；
`schedule` 有详情 tab，但没有「下一次什么时候、要不要现在跑」的一览。

### 2.3 再看用户真实处境（本机装机现状）

已装 7 个第三方插件：插件市场、账本（成本）、技能浏览器、IM、心情/鲸鱼宠物、增强侧栏。
它们分别覆盖：**发现**（市场）、**记账**（账本）、**能力目录**（技能）、**陪伴**（宠物）、**工作台**（侧栏）。
覆盖「运行中状态 + 人的放行」的：**零**。

一个可观察的连锁反应：装了账本的人知道「这次会话花了不少」，但仍然不知道
「是不是有个目标在空转、是不是有个作业在重试、是不是该让它停下」。
**钱是滞后指标，状态是先行指标。** 账本告诉你昨天花了多少，塔台告诉你现在该不该按停。

## 3. 用户与 JTBD

| 用户 | 场景 | 现在怎么做 | 想要什么 |
|---|---|---|---|
| 单人重度用户（本机就是） | 同时开 3–5 个会话，其中一个挂着 goal 自动续轮 | 轮流点左侧会话 | 「有没有事」一个数字；有事直接处理 |
| 长任务用户 | 让 agent 跑 20 分钟的构建/迁移 | 守着，或过一会儿回来看 | 不用守；结束了/失败了能立刻知道 |
| 自动化用户 | 定时任务 + 夜间跑 | 第二天回来翻结果 | 一眼看出昨晚谁成功、谁卡住 |
| 小团队（未来付费） | 多人多机各跑各的 | 口头同步、群里问 | 一张共享的「在飞」镜面 + 审计 |

**JTBD 一句话**：当我放手让 agent 自己跑时，我要在**不打断当前工作的前提下**知道它是否还健康，
并且能在**一步之内**让它继续或停下。

## 4. 竞品分析（三层，逐层说明为什么还有缝）

### 4.1 第一层：同生态右栏插件（28 个 tab + 4 viewer + 4 增强）

来源：[DSH-better-sidebar](https://github.com/omdsh-dev/DSH-better-sidebar) 的生态目录
（[topic](https://github.com/topics/dsh-better-sidebar) 已收录 30+ 插件）。按能力归并：

| 类别 | 代表 | 它们强在哪 | 它们的盲区 |
|---|---|---|---|
| 文件/编辑器/资源管理 | files、editor、Explorer-Plus、excel-panel | 把工作区搬进侧栏 | 只管产物，不管「谁在生产」 |
| 代码审阅/变更 | diff、file-review-tab、turn-review | 逐行、逐轮审 | 事后的，且以文件为单位；不看运行态 |
| 会话辅助 | sidechat、sidebar-qa、sidenote、sidenote 类 | 边聊边问 | 是「再开一个对话」，不是「看住一批运行」 |
| 会话结构/导航 | conversation-outline、turn-outline、flowglass | 把长会话折叠/可视化 | 只读、只解释，**不提供干预动作** |
| 外部连接 | git-remotes、git-forge、ssh-tunnel、egress 类 | 把外部世界接进来 | 与 agent 运行状态无关 |
| 能力/自动化 | skill-sidebar、skill-explorer、sentinel、starter | 能力目录、条件唤醒、运行配置 | sentinel 最接近（会唤醒 agent），但它是**事件驱动**，不是**人的值守面** |
| 展示/装饰 | icons、terminal-plus、quicklook、preview-select | 体验打磨 | 不解决调度 |

**结论**：这一层已经把「看内容」做满了，把「看运行」留空了。
而且它们全部是**每会话、只读、无动作**的形态 —— 塔台是**跨会话、可动作**的形态。

### 4.2 第二层：相邻能力（本机已装或宿主自带）

| 对手 | 它做什么 | 与塔台的关系 | 差异点 |
|---|---|---|---|
| 账本 ledger（本机已装） | token/成本归因、预算、压缩对照 | **互补，不是竞争** | 钱是结果；塔台是状态与放行。共用「本机只读」的信任底座 |
| 内置 schedule tab | 单个定时任务的详情 | 部分重叠 | 塔台给「全机的下一次」与「立即执行」 |
| 内置 subagent tab / plan tab | 子代理、计划 | 部分重叠 | 塔台把它们放进「谁在飞」的同一张表 |
| dsh-market | 发现与安装 | 渠道 | 塔台是它货架上的商品 |

### 4.3 第三层：外部商业产品（为什么这块地还没有人正面占）

| 产品/品类 | 定价与形态 | 做了什么 | 为什么不能直接替代 |
|---|---|---|---|
| [LangSmith / Langfuse](https://www.morphllm.com/comparisons/langsmith-alternatives) 类可观测平台 | 按 seat/事件，云为主，可自托管 | trace、prompt、eval、数据集 | 面向**开发者调试**，重、要接 SDK、默认出网；不解决「本机现在要不要按停」 |
| Helicone / 网关类 | 按量，云 | 成本与限流 | 只覆盖模型调用，不覆盖 agent 的作业/目标/定时 |
| [paperclip](https://github.com/paperclipai/paperclip) 类「AI 代理团队编排」 | 项目制，Web 平台 | 多 agent 编排、看板 | 自带一套编排世界观，要求把工作流搬进它那里；DSH 用户要的是**留在我自己的工作台里** |
| Devin / Cursor 后台任务类的运行面板 | 订阅制 | 云端 agent 的任务列表与接管 | 绑定各自云；本地 harness 无法用 |
| VS Code / IDE 的任务与调试面板 | 免费 | 进程、任务、断点 | 不理解 agent 语义（goal / 轮次 / 待处置） |

**空白定位（一句话）**：
> 云平台卖「把你的 agent 数据交给我」，塔台卖「你的 agent 数据一步都不用离开这台机器，我照样让你管得住」。

这是个**结构性差异，不是功能差异**：可观测平台的商业模式要求数据集中，而本地 agent 用户的核心资产恰恰是
「代码 + 对话 + 凭证」不出域。谁把「集中」当默认，谁就吃不到这批人。

### 4.4 批判性思维：我否掉的四个方向

| 否掉的方向 | 表面理由 | 否决理由（第一性原理） |
|---|---|---|
| 又一个成本面板 | 账本已验证有需求 | 已被占；且**钱不能指导当下动作**——看到花了 ¥3 你也不知道该按停哪个 |
| 又一个文件/预览器 | 生态里最多、最好抄 | 16 个占用者已饱和；边际价值趋零，价格战 |
| 侧边聊天/划词追问 | 3 个竞品在做 | 它增加**对话**，而瓶颈是**决策次数**；越聊越累 |
| 会话流程图（flowglass 类） | 好看、技术炫 | 只解释不干预；用户看完还是要自己去找按钮。「可视化 ≠ 可操纵」 |
| 纯通知/告警（webhook 推送） | 简单 | 推送解决「知道」，不解决「处置」；且需要外部通道，破坏本地性。作为 Pro 功能而非核心 |

**统一原则**：任何不能把「决策次数」降下来的功能，都不进 v1。

## 5. 产品定义（v0.1 已实现）

### 5.1 信息架构（一屏四段，从上到下按「要不要你」排序）

1. **计数条**：在飞 / 待处置 / 后台 / 定时 —— 四个数字，红黄绿。
2. **需要你**：只由确定性规则产生，最多 20 条，紧急在前：
   - 目标 `blocked`（附宿主给的受阻原因）
   - 后台作业 `failed`（10 分钟内）
   - 目标 `paused`（等你决定是否继续）
3. **航班**：每个活 agent 一行/一卡。根会话在前、子代理紧随；显示工作区名、短 id、
   目标原文（3 行截断）、第 n/m 轮、进度条、在跑标记、作业数、失败数；动作：打开会话 / 暂停 / 继续 / 完成。
4. **后台作业**：运行中与失败项，显示标签、耗时、输出体积、最近进度；动作：终止。
5. **定时航班**：未结束的定时任务，显示下一次执行与状态；动作：立即执行。

### 5.2 交互原则

- **一次点击一个动作**：不做批量、不做自动重试、不做乐观更新。失败就在原地用中文说清原因。
- **乐观并发**：所有目标动作带 `revision`，别人改过就报冲突，绝不覆盖。
- **只作用于活着的 agent**：会话关了就没有动作对象，这是物理事实，不伪装。
- **可放弃**：面板关掉即卸载，轮询停止；不留后台定时器、不改任何宿主配置。

### 5.3 明确不做（反功能清单）

- 不做 LLM 摘要、不做「智能判断该不该停」——先让确定性规则跑通，模型判断是 v2 的可选层。
- 不读消息内容、不读文件内容、不存历史。
- 不做第二套通知系统（不弹系统通知、不发 webhook，v0.1）。
- 不接管「审批 / 提问」队列（`ask_user_question` 的等待中列表没有稳定只读接口，**不猜**）。

## 6. 差异化：三条不容易被抄的

1. **跨会话 + 可动作**。生态里 28 个 tab 几乎全是「每会话、只读」。
   跨会话意味着数据源必须是宿主级服务（`agents` / `goals` / `jobs` / `schedule`），
   而不是会话投影 —— 后来者抄界面容易，抄「对的动作 + 并发语义」难。
2. **把「状态」而不是「内容」作为一等公民**。内容类插件可以互相替代，状态类不行：
   一旦用户把「看塔台」变成开机习惯，替换成本是行为习惯，不是功能对比。
3. **本地性作为产品约束而非卖点**。不落盘、不出网、不建账号。
   这同时是最强的企业销售话术（数据不出域）和最强的工程约束（没有服务端可维护，只能把客户端做好）。

## 7. 商业模式（假设，未验证）

### 7.1 三档

| 档位 | 内容 | 定价（假设） | 为什么这样切 |
|---|---|---|---|
| **开源版**（本仓库现状） | 单机值守、全部动作、7 天注意力窗口 | 免费，Apache-2.0 | 分发与信任；动作能力不阉割，阉割的是「协作与留存」 |
| **Pro**（个人） | 审计留存与导出、告警外发（飞书/企微/Webhook）、自定义规则（如「作业跑超 10 分钟即提醒」）、多机汇聚 | ¥69/年 或 ¥9/月 | 个人愿意为「不用守着」付小钱；边际成本≈0，毛利极高 |
| **Team**（5–50 人） | 共享只读镜面、按人/项目的运行视图、策略下发（超时自动暂停、失败次数上限）、审计导出 | ¥39/席/月（年付） | 商业分界线是「有没有治理」，不是「功能多少」 |
| **Enterprise** | 私有化、SSO、不可篡改审计、SLA | 年框 License | 数据不出域是硬需求，本地优先架构天然合规 |

### 7.2 单位经济（可算的部分）

- 边际成本：一次快照 = 一次内存遍历（本机 4 个 agent，实测响应 < 10ms 量级），无外部调用。
  **每用户边际成本 ≈ 0**，所以定价的锚不是成本，是「一次误判/一次空转」的机会成本。
- 付费意愿的锚点：账本已经证明「本机用户愿意为看清花了多少付费」；
  塔台卖的是「看清该不该继续」，比钱更贴近当下动作，锚点更高。

### 7.3 为什么不做 SaaS

做 SaaS 就要收数据，收数据就丢掉「不出域」这个唯一的、结构性的差异化。
**宁可少一个增长杠杆，也不放弃护城河。**

## 8. GTM（生态分发，不买量）

1. **蹭基础设施的流量**：better-sidebar 是事实标准（本机已装，30+ 插件生态）。
   塔台只依赖它的 `sidebarRightTabs` + 两个 keyed seat，装它就自动出现在右栏，**零配置**。
2. **插件市场货架**：本机已装 dshmarket，`dsh-plugin-*` 命名可被检索。
3. **启动套件**：社区已有「一键整合包」类的分发形态（如 [dsh-starter-kit](https://github.com/SOCOOL666/dsh-starter-kit)），
   塔台属于「装完就该有」的那一类（和增强侧栏同级），适合作为默认预置项谈。
4. **与账本组套**：「灵搭」同一发行方可把 **账本（钱）+ 塔台（人）+ 未来审计（责）** 打成一套运行治理套件，
   单卖一个插件获客成本高，套件提升客单与留存。
5. **内容抓手**：一篇「我给 5 个 agent 装了个塔台」的实测文，比任何功能列表有效 —— 因为痛点是可共鸣的。

## 9. 路线图

| 版本 | 主题 | 关键项 |
|---|---|---|
| **v0.1（本次）** | 能看见、能按住 | 全机航班、目标三动作、作业终止、定时立即执行、角标入口 |
| v0.2 | 不漏 | 已关闭会话的目标状态（从 session log 只读回放）；作业历史（近 24h）；`ask_user_question` 等待中列表（等宿主给出稳定只读接口再做） |
| v0.3 | 提醒 | 本地系统通知；「静默 30 分钟无变化」检测；规则引擎（超时/失败次数） |
| v1.0 | 可协作 | 多机汇聚（只读镜面）、审计导出、Team 策略 |
| v2.0 | 会判断 | 可选 LLM 摘要：「这个目标在原地打转」；建议动作但**不自动执行** |

**排序原则**：先确定性、后概率性；先单机、后多机；先动作、后智能。
一个会误判的「智能暂停」比没有智能更伤信任。

## 10. 风险与反脆弱

| 风险 | 影响 | 处置 |
|---|---|---|
| 宿主 `@Remote` 契约漂移 | 面板某块变空 | 所有服务经 `ctx.get` 可选获取，缺失即降级空数组；动作失败原样回传，不假装成功 |
| 换代码需重启才生效 | 升级体验断档 | 已在 README 显式写明；v0.2 考虑用 `configEditor` 的可变字段承载规则，减少代码热更依赖 |
| 只有活 agent 可见 | 关掉的会话「消失」 | 这是 v0.1 的**诚实边界**，写进 UI 文案与文档；v0.2 补只读回放 |
| 轮询开销 | 多 agent 时 CPU 抖动 | 双档（4s/9s）、隐藏即停、面板关即卸载；实测快照为纯内存遍历 |
| 动作误触 | 停错目标 | 一次一个动作 + `revision` 乐观并发 + 只对活 agent 生效 + 危险动作用红色语义 |
| 「又一个面板」的疲劳 | 装了不用 | 全部价值压缩到「一个数字 + 一次点击」；入口带红角标，让它在没事时**安静** |

---

## 11. 成功指标（先定怎么算赢）

| 指标 | 定义 | v0.1 目标 |
|---|---|---|
| 值守率 | 7 日内打开过塔台的活跃用户占比 | > 40%（装了的人） |
| 干预时延 | 目标 blocked → 人处置的中位时长 | 从「下次想起来」降到 < 10 分钟 |
| 无人值守时长 | 有 goal 在跑而人离开的时长 | 上升（说明信任建立） |
| 误触率 | 24h 内被撤销/恢复的动作占比 | < 5% |
| 留存 | 次周仍在使用（有动作或打开 ≥3 次） | > 35% |

**北极星**：`每周完成的「人工放行」次数` —— 它同时代表 agent 在自主干活、和人在有效治理。

## 12. 一页纸结论

- **问题**：agent 越来越自主，人的瓶颈从「怎么做」变成「要不要继续」；而界面只给了信息，没给放行。
- **证据**：整份 slot 清单里 `goal` 只出现在工具名里；右栏 16 个占用者无一呈现目标；生态 28 个 tab 全是「每会话只读」。
- **方案**：右侧栏「塔台」——跨会话的 在飞 / 待你处置 / 后台 / 定时，一屏 + 一次点击的干预。
- **差异**：跨会话可动作（不是可视化）、状态一等公民（不是内容）、本地优先（不出域）。
- **商业**：免费单机 → Pro 提醒与留存 → Team 治理 → 企业私有化；边际成本≈0，护城河是「不出域」。
- **诚实**：v0.1 只覆盖活着的 agent，不含模型判断，不含通知；这些是路线图，不是已交付。
