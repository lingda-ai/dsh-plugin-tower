# 评估：塔台是否应读取账本的成本数据

> 评估对象：把「账本」的成本数据接入塔台的值守报告（不含面板）。
> 结论：**值得做，但只在报告里做，且必须先解决口径；不要放进面板。**

---

## 1. 先看事实：账本快照长什么样

真实文件：`~/.dsh/ledger/session-<id>.json`（检查时 12,185 字节，随会话约 3 秒刷新）

```jsonc
{
  "version": 1,                     // ← 生产者已经声明了 schema 版本
  "generatedAt": "2026-11-21T06:51:15.205Z",
  "sessionId": "session-bc835d33-…",
  "totals": {
    "cost": { "amount": 1.653827, "currency": "CNY", "knownEntries": 138, "unknownEntries": 0, "parts": {…} },
    "saved": { "amount": 65.0657, "currency": "CNY", "entries": 138 },
    "tokens": { "input": 55953, "output": 135001, "cacheRead": 66393600, … },
    "entries": 138, "cacheHitRate": 0.9992, "savedShare": 0.9752
  },
  "topSources": [{ "plugin": "unattributed", "amount": 1.653827 }],
  "recent": [ { "at": 1795243411871, "turn": 16, "step": 14, "amount": 0.0126, "kind": "model", … } ],  // 最多 20 条
  "peak": { "amount": 0.0182, "turn": 17, "step": 1, "model": "deepseek-flash" },
  "overview": [{ "sessionId": "…", "amount": 1.653827, "entries": 138, "lastAt": 1795243875205 }],
  "budget": null,
  "pricing": { "kind": "file", "asOf": "2026-11-20", "source": "manual: …", "rejected": [] },
  "truncated": false
}
```

**可行性判断：比预期好。** 理由：

- `version: 1` —— 这不是一坨私有格式，而是**带版本的自描述快照**；
- `unknownEntries` / `pricing.asOf` / `truncated` —— 生产者已经把「哪些算不出来」和「快照是否完整」交代了；
- `currency` 显式存在 —— 不会出现跨币种盲加。

---

## 2. 但有三个口径问题，不解决就不能显示

| 问题 | 事实 | 后果 |
|---|---|---|
| **不是窗口增量** | `totals.cost` 是**该会话自开始以来的累计**；`recent[]` 有 `at` 但只保留 20 条 | 一个跑了 3 天的会话，把它塞进「最近 24 小时」报告 = **虚假的时间口径** |
| **可能是旧数** | 快照由账本自己的 3s 循环写；账本停掉后文件冻结 | 不做陈旧检测，就会把昨天的钱当成今天的 |
| **汇总语义未定义** | 文件是「每会话一份」，`overview[]` 又是另一份聚合 | 同时用两者 = 重复计数 |

**能站住的唯一写法**：不做「最近 24h 花了多少」，而做
**「本次值守涉及的会话，自开始以来累计 ¥X（按本地费率估算；N 条费率未知）」**，
并且只纳入 `lastAt` 落在窗口内的会话。

这是**口径上的降级**，但它是诚实的；而一个含糊的成本数字在管理场景里比没有更危险。

---

## 3. 价值：对谁值，对谁不值

| 角色 | 增量价值 | 判断 |
|---|---|---|
| 个人用户 | 低 —— 打开「账本」tab 就能看到同样的数 | **不值**（重复展示） |
| 班组/团队负责人 | 高 —— 交接时要回答三件事：**做了什么 / 花了多少 / 有没有问题**；报告目前缺第二件 | **值** |
| 企业/合规 | 中高 —— 成本与审计同页，才叫「运行治理」而不只是「运行监控」 | 值 |

**量化锚点（来自真实快照）**：本会话花费 **¥1.6538 / 138 次调用**，而缓存已省 **¥65.07** ——
省下的钱是花掉的 **约 39 倍**。这一行放进交接报告，比任何功能列表都更能说明「为什么要治理」。

**另一个价值**：它是「账本管钱 + 塔台管人 + 审计管责」套件叙事的**第一次真正接线**，
而套件正是商业化方案里提高客单的手段。

---

## 4. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 格式耦合 | 读别人的私有文件，对方一变就断 | 只接受 `version === 1`；字段缺失或类型不符 → **整段隐藏**，绝不显示 0 |
| 定位漂移 | 塔台一旦在面板里显示成本，就变成「又一个成本仪表盘」，与账本边界模糊 | **只进报告，不进面板** |
| 陈旧/截断误读 | 旧快照、`truncated: true` | 显示 `generatedAt` 与「可能已过期」；`truncated` 时明确写「快照不完整」 |
| 隐私 | 报告是要转发出去的文档 | 报告首部已声明「不含对话内容」；成本属金额，不含内容，可接受 |

---

## 5. 落地状态（2026-11-21）

- **阶段 0 已交付（0.7.0）**：塔台只读账本快照，报告新增成本节；双模口径（有 `window` 用窗口，否则累计并写明）；
  缺席/坏文件/多币种/陈旧全部按「不可读就隐藏或标注」处理。`test/ledger-bridge.mjs` 22 条。
- **阶段 1 待做（在账本侧）**：给快照加 `window: { hours, cost, entries, unknownEntries }`。
  塔台已能直接消费，加完即可自动从「累计」升级为「窗口增量」，**塔台不需要改代码**。

## 5b. 推荐路径（决策当时的原文，按顺序，前两步便宜）

**阶段 0（半天，可立刻做）**
塔台在报告里加一节「成本（来自账本）」：
- 只读 `~/.dsh/ledger/*.json`，`version !== 1` 跳过；
- 只统计 `lastAt` 落在窗口内的会话，求和 `totals.cost.amount` 与 `unknownEntries`；
- 文案写死口径：**「窗口内活跃会话的累计，按本地费率估算，其中 N 条费率未知」**；
- 账本不在/不可读 → **整节不出现**（不是显示 ¥0）。

**阶段 1（半天，推荐做在账本侧）**
给账本快照加 `window: { hours, cost, entries }`（生产者自己算窗口增量）。
塔台改读这个字段，口径立刻从「累计」升级为「窗口内增量」。
—— **这是把契约放在数据生产者一侧，比消费者猜字段可靠得多。**

**阶段 2（可选）**
报告里加「最贵一次调用」与「缓存节省额」，这两个字段已经现成（`peak` / `totals.saved`）。

---

## 6. 判定标准（Go / No-Go）

**做**，当且仅当：报告的使用者是团队/企业（有交接与汇报场景）。
**不做**（或只做阶段 1 之后），如果：

- 账本快照在 3 个自然月内改过 2 次以上结构 —— 说明格式还在动，此时接线是负债；
- 目标用户主要是个人 —— 他们开账本 tab 更快；
- 无法接受「累计而非窗口」的口径 —— 那就必须先在账本侧补 `window` 字段。

---

## 7. 一句话结论

**技术上可行（对方已经版本化），价值集中在团队与企业，且必须以「报告里的一节、口径写死、不可读就整段消失」的形态出现。**
先做阶段 0 + 阶段 1；面板一行都不要加。
