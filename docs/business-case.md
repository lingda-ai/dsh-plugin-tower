# 塔台 · 商业化可行性方案

> 结论先行，再给推导。每个数字标注来源类型：**【实测】** 可复算、**【推算】** 基于实测的换算、**【假设】** 待验证的猜测。
> 配套：`product-plan.md`（产品怎么长）、`product-brief.md`（为什么是这个方向）。

---

## 0. 结论（先看这一段）

1. **单卖这个插件不成立。** 生态分发是幂律的：头部插件月下载 38.5 万，同样打磨过的账本只有 **81/月**【实测】。
   靠「一个插件 + 个人订阅」养活不了人。
2. **成立的是「运行治理套件 + 企业交付」。** 塔台负责开源获客与信任，钱从 **团队治理（L3）与审计（L4）** 收。
3. **首年合理区间：基准 ¥20–55 万，乐观 ¥80–150 万，保守 < ¥3 万**【推算】。
   基准情形需要 3–5 家企业客户，而**不是**几千个 Pro。
4. **做不做，取决于 90 天内四个闸门（G1–G4）。** 过不了就退回「纯开源 + 品牌资产」，不投商业版。
5. **最大的风险不是竞品，是平台吞并**：DSH 官方内置一个目标面板，L1 立刻被商品化。
   对策不是防守，而是把价值上移到官方不会做的 **审计与治理**。

### 1.1 生态分发实测（npm 上月下载，2026-10-21 ~ 11-19）【实测】

| 包 | 月下载 | 周下载 | 说明 |

| `dsh-better-sidebar` | **385,543** | 90,785 | 右栏底座，5,268 star / 515 fork（GitHub，2026-11-21） |
| `@linxin666/dsh-client-ui-skill-explorer` | 164,551 | 28,969 | 技能浏览器 |
| `@xmanrui/dsh-im` | 144,737 | 23,368 | IM 集成 |
| `dsh-plugin-whale-pet` | 22,818 | 2,606 | 宠物（装饰类） |
| `dsh-bloub-mood` | 2,360 | 283 | 心情（装饰类） |
| `dsh-plugin-ledger` | **81** | 8 | 同一发行方的成本插件 |

**三个可用结论**：

1. **量级是幂律的**，头部与长尾差 4 个数量级。功能质量不是分布的主因 ——
   skill-explorer（16 万）与 bloub-mood（2 千）的差距，远大于它们的功能复杂度差距。
2. **高的那几个几乎都"在默认组合里"**：市场、侧栏底座、被整合包预装的工具。
   → **分发的主战场是"被装进去"，不是"被搜到"。**
3. **账本 81/月是同一作者的实测反证**：一个真正的工具型插件，在没有渠道推的情况下就是这个量级。
   任何「靠订阅赚钱」的模型都必须先解释这 81。

> 口径提醒：npm 下载 ≠ 装机量 ≠ 活跃用户。CI、重装、镜像都会放大。下文一律用「月下载/10」做保守换算【假设】。

## 2. 为什么"单插件订阅"不成立

三个乘数同时很小：

```
收入 = 装机量 × 付费率 × 客单价
     = 38.5k × 2% × ¥99
     ≈ ¥7.6 万/年        ← 且这是"整个生态"的乐观值，不是塔台一家的
```

- **装机量**受幂律限制（账本 81/月为证）；
- **付费率**受中国开发者习惯限制（工具类 1–3%，无销售触达）；
- **客单价**受"它只是一个侧栏面板"的心智限制。

**反推**：要让这门生意一个人干得下去，年收入需 ≥ ¥20–30 万【假设：机会成本】。
用订阅达成，需要 2,000–3,000 个付费个人 —— 在月活装机 3.8 万的池子里等于 5–8% 付费率，
**对一个非刚需的效率面板，这不现实**。

**必须换公式**：

```
收入 = 企业客户数 × 企业客单价 − 交付成本
     = 4 × ¥10 万 − ¥12 万 ≈ ¥28 万/年
```

这就是本方案主张的重心：**开源插件获客 → 企业治理/审计收钱**。

## 3. 四种收入模型对比与取舍

| 模型 | 客单价 | 获客成本 | 交付成本 | 适配度 | 判断 |
|---|---|---|---|---|---|
| 开源赞助/打赏 | ¥0–100 一次性 | 极低 | 0 | 低 | 只做信任，不做收入 |
| 个人 Pro 订阅 | ¥99/年 | 低 | 0 | 中 | 有量才有钱；量被幂律锁死 → **作为转化漏斗，不作为主营收** |
| 团队版 | ¥39/席/月（≥5 席） | 中 | 低 | 高 | **商业分界线**：卖的是"多人一起看 + 策略" |
| 企业私有化 | ¥8–15 万/年 | 高（需销售） | 中（部署+支持） | 高 | **真正的利润来源**：卖的是"出事能证明" |
| 定制/培训 | ¥8k/天 | 中 | 高 | 中 | 现金流补充，非产品 |

**取舍**：主营收 = 企业私有化；次营收 = 团队版；Pro 只做漏斗与口碑。

## 4. 定价与包装

### 4.1 四档

| 档位 | 内容 | 价格【假设】 | 定价理由 |
|---|---|---|---|
| 开源版 | L1 全量动作 + 7 天注意力窗口，Apache-2.0 | ¥0 | 获客与信任；**动作能力不阉割**，阉割的只有留存与协作 |
| Pro（个人） | L2 提醒 + 规则 + 90 天留存 + 导出 | **¥99/年**（早鸟 ¥69） | 锚点是"少守一小时"，时薪 ¥50–100 的开发者一次就回本 |
| Team（5–50 人） | L3 治理：共享镜面、策略下发、审计导出、48h 支持 | **¥39/席/月**（年付） | 对标国内研发工具 ¥20–60/席/月；卖治理不卖功能 |
| Enterprise | L4 审计：脱敏、留存策略、不可篡改导出、离线 License、8h 支持、私有化 | **¥8–15 万/年** | 对标研发效能/合规工具；含部署与年度审计支持 |

### 4.2 套件打包（提高客单的关键）

| 套件 | 内容 | 价格【假设】 |
|---|---|---|
| 运行治理套件（团队） | 账本 + 塔台 + 审计导出 | **¥149/席/年** |
| 运行治理套件（企业） | 同上 + 私有化 + 离线 License + 年度巡检 | **¥15–25 万/年** |

理由：账本解决"钱"、塔台解决"人"、审计解决"责"。
单卖任何一个都是工具，合起来才是**治理系统** —— 而企业只为系统付钱。

### 4.3 绝不做的定价

- 不按 token / 运行次数计费（与"少看"的价值主张冲突）
- 不做"功能解锁式"阉割（免费层必须完整，否则拿不到口碑）
- 不做必须联网的 License 校验（破坏"不出域"，见 §7）

## 5. 成本结构与盈亏平衡

### 5.1 成本【推算/假设】

| 项 | 单人（兼职） | 2 人小组 |
|---|---|---|
| 人力 | ¥20–30 万/年（机会成本） | ¥55–70 万/年 |
| 宿主兼容维护（4 人日/月） | 含在人力 | 含在人力 |
| 企业交付/支持（2 人日/月/家） | — | 含在人力 |
| 合规一次性（软著/等保材料） | ¥1–3 万 | ¥3–5 万 |
| 服务器 | **¥0**（全本地，无后端） | ¥0 |
| 分发 | ¥0（生态渠道） | ¥0 |

**结构性优势**：没有后端 = 边际成本≈0、没有运维、没有数据合规风险。
**结构性劣势**：没有服务端 = 无法做账号、联网授权、云端协作 → 团队能力只能做到"只读镜面"。

### 5.2 盈亏平衡

| 目标 | 需要什么 |
|---|---|
| 覆盖单人机会成本（¥25 万） | 3 家企业单（¥8 万）**或** 100 Pro + 25 个团队（5 席） |
| 覆盖 2 人小组（¥60 万） | 8 家企业单 **或** 5 企业 + 30 团队 + 200 Pro |

### 5.3 三档情景（首年）

| 情景 | 假设 | 收入 | 概率判断 |
|---|---|---|---|
| 保守 | 不投商业版，只有开源 + 少量 Pro | **< ¥3 万** | 高（若 G1 未过） |
| 基准 | 过 G1–G3；签 3–5 家企业 + 20 个团队 | **¥20–55 万** | 中 |
| 乐观 | 套件进入默认组合 + 8 家企业 + 渠道分成 | **¥80–150 万** | 低–中 |

**结论**：这是一个**小而稳**的生意（¥20–60 万/年量级），不是风险投资的标的。
若目标是"养活 1–2 个人 + 建立品牌"，可行；若目标是"高速增长"，不成立。

## 6. 竞争与护城河

| 维度 | 现状 | 可防守性 |
|---|---|---|
| 本地优先 | 所有可观测平台都要求数据集中 | **强**（结构性，不是功能） |
| 套件连带 | 账本已在同作者手上 | 中（需要两件都好） |
| 契约守卫积累 | 宿主 API 漂移是真实成本，踩过的坑是壁垒 | 中（时间壁垒） |
| 生态位先发 | 右栏尚无运行治理面 | 弱–中（会被抄） |
| 品牌（灵搭 / DSH 生态） | 已在生态内有作品 | 中 |

**最容易被抄的是界面，最不容易的是**：
①「不出域」的商业模式选择（抄功能容易，放弃云端难）；
② 跨版本稳定性（每个宿主版本的坑）；
③ 与账本组成"钱+人+责"的完整叙事。

## 7. 平台风险与合规

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| DSH 官方内置 goal/运行面板 | 中高 | L1 被商品化 | 价值上移到 L3/L4；Apache-2.0 允许被官方吸纳（被合并=分发胜利） |
| better-sidebar 变更扩展 API | 中 | 入口失效 | 已只依赖宿主原生 `sidebarRightTabs` + seat，不强绑定 better-sidebar 私有 API |
| 宿主 `@Remote` 契约漂移 | 高（长期） | 区块失效 | 全路径 `ctx.get` 可选 + 30 条冒烟断言 + 兼容矩阵 |
| 分发被单一渠道控制 | 中 | 量断崖 | 同时铺 Gitee/GitHub/npm/整合包/社群 |

**合规设计（同时是卖点）**：
- 数据不出域、无账号、无遥测（匿名统计默认关）
- 审计导出为本地文件 + 哈希链，第三方可独立校验
- 企业版**离线 License 文件**校验，不联网激活
- 开源 Apache-2.0（含专利授权），便于企业法务通过

## 8. 90 天验证计划与 Kill 标准

### 阶段

| 周 | 动作 | 产出 |
|---|---|---|
| W1–2 | 发布 Gitee + GitHub 镜像；向 better-sidebar 生态目录提 PR；写一篇实测文（掘金/知乎/公众号）；申请进 1–2 个"一键整合包" | 可安装版本 + 3 个渠道曝光 |
| W3–4 | 看分发：安装量、star、issue | G1 判定 |
| W5–6 | 10 场 30 分钟访谈（重用户 + 团队负责人）：现在怎么确认 agent 状态、愿不愿付费、愿付多少 | G2/G3 判定 |
| W7–10 | 做 L2+L3 最小版（通知 + 审计导出），给 3 家免费试用 | 试用反馈 + 付费意向书 |
| W11–12 | 决策会 | 继续 / 转向 / 停 |

### 闸门（不过就停，不给自己找理由）

| 闸门 | 标准 | 未过的含义 |
|---|---|---|
| **G1 需求真实** | 30 天内安装 ≥ 300（或等价：star ≥ 30 且 issue ≥ 5 条真实需求） | 分发放大或需求不足 → 不投商业版 |
| **G2 习惯成立** | 抽样中次周留存 ≥ 25%（打开 ≥3 次/周） | 装了不用 → 退回"装饰性面板"，不做 |
| **G3 付费意愿** | 10 家中 ≥ 3 家愿为「审计导出 + 告警」付 ≥ ¥2,000/年 | 只愿白嫖 → 转纯开源 + 企业定制 |
| **G4 平台空间** | 6 个月内 DSH 官方未内置等价的运行面板 | 官方已做 → 立刻转 L4 审计，放弃 L1 投入 |

**G3 是唯一真正的生死线**：技术可行性已被 v0.1 证明，需求与付费意愿尚未证明。

## 9. GTM：按"杠杆从高到低"排

1. **进默认组合（最高杠杆，唯一能突破幂律的方式）**
   一键整合包、市场推荐位、better-sidebar 的 start page 卡片、生态目录收录。
   实测显示高下载量的插件几乎都在这类位置，而不是靠搜索。
2. **与账本组套交叉销售**：同一批用户、同一套叙事（钱+人+责），获客成本摊薄。
3. **实测内容**："我给 5 个 agent 装了个塔台"——痛点可共鸣，转化高于功能列表。
4. **社群口碑**：issue 24h 内响应；把真实用户案例写进 README。
5. **企业直销**：走灵搭现有客户与 DSH 企业用户，用"私有化 + 审计"切入，不用插件订阅做企业单。

## 10. 决策建议

**建议：做，但按"小生意"做，不按"创业项目"做。**

- 立刻做（0–30 天）：发版、进 2 个渠道、写 1 篇实测文 → 拿 G1。
- 只在 G1 通过后投入：L2 提醒 + 审计导出（约 2 周）。
- 收入重心从第一天就放在**企业交付**，个人 Pro 只当漏斗。
- 把塔台与账本合并叙述为「运行治理套件」，单插件不单独定价。
- 不为"增长"引入云端或遥测 —— 那是把唯一的护城河卖掉换短期数据。

**一句话**：**用开源换信任，用审计换钱，用套件换客单。**
